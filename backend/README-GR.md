# Backend της ιστοσελίδας DISTILLOGIC

## 1. Τι είναι το backend

Η ιστοσελίδα αποτελείται πλέον από δύο μέρη:

- **Frontend:** Τα HTML, CSS και JavaScript που φορτώνει ο browser και βλέπει ο επισκέπτης.
- **Backend:** Ο ιδιωτικός κώδικας που εκτελείται στον server. Παραλαμβάνει τη φόρμα, ελέγχει τα στοιχεία και αργότερα θα τα προωθεί με ασφάλεια στο CRM.

Το frontend δεν πρέπει να επικοινωνεί απευθείας με το CRM, επειδή τότε το μυστικό API token του CRM θα ήταν ορατό σε κάθε επισκέπτη. Το token θα υπάρχει μόνο στο ιδιωτικό αρχείο `.env` του server.

## 2. Ροή ενός αιτήματος

1. Ο επισκέπτης ανοίγει το **Discuss a Project**.
2. Συμπληρώνει τα πεδία και επιλέγει τη συγκατάθεση επεξεργασίας.
3. Ο browser στέλνει κρυπτογραφημένο HTTPS αίτημα στο `POST /api/project-enquiries`.
4. Ο backend ελέγχει τα υποχρεωτικά πεδία, το email, τις επιτρεπτές επιλογές και τα αρχεία.
5. Εφαρμόζεται όριο πέντε προσπαθειών ανά δεκαπέντε λεπτά ανά IP.
6. Δημιουργείται μοναδικός κωδικός αναφοράς, όπως `DL-A1B2C3D4`.
7. Σε δοκιμαστική λειτουργία το αίτημα απορρίπτεται από την αποθήκευση αφού ολοκληρωθούν οι έλεγχοι. Σε παραγωγή θα προωθείται στο CRM.
8. Ο browser εμφανίζει στον επισκέπτη την τελική κατάσταση.

## 3. Τι έχει υλοποιηθεί

- Node.js 20+ και Express.
- `GET /api/health` για έλεγχο ότι ο server λειτουργεί.
- `POST /api/project-enquiries` για τη φόρμα έργου.
- Έλεγχος τύπου, μήκους και εγκυρότητας όλων των πεδίων.
- Σταθεροί εσωτερικοί κωδικοί επιλογών, ανεξάρτητοι από τη γλώσσα EN/GR.
- Υποχρεωτική συγκατάθεση τόσο στο frontend όσο και στο backend.
- Honeypot πεδίο για απλά αυτοματοποιημένα bots.
- Rate limiting κατά μαζικών αποστολών.
- Μέχρι 5 αρχεία, 10 MB ανά αρχείο και 25 MB συνολικά.
- Επιτρεπτοί τύποι: PDF, DOC, DOCX, XLS και XLSX.
- Security headers μέσω Helmet.
- Απόκρυψη της τεχνολογίας του server από το HTTP header.
- Αρχεία upload μόνο στη μνήμη. Στο mock mode απορρίπτονται και δεν γράφονται στον δίσκο.
- Αυτόματοι έλεγχοι για health, έγκυρη υποβολή και μη έγκυρα στοιχεία.

## 4. Δοκιμαστική λειτουργία

Το `.env` περιέχει:

```text
ENQUIRY_DESTINATION=mock
```

Σε αυτή τη λειτουργία ο server κάνει όλους τους ελέγχους αλλά **δεν αποθηκεύει και δεν στέλνει προσωπικά δεδομένα**. Η σελίδα ενημερώνει καθαρά ότι το αίτημα επικυρώθηκε μόνο σε test mode.

Η εφαρμογή αρνείται να ξεκινήσει με `NODE_ENV=production` και `ENQUIRY_DESTINATION=mock`. Αυτό αποτρέπει το ενδεχόμενο να ανέβει κατά λάθος μια φόρμα που φαίνεται ενεργή αλλά χάνει πραγματικά αιτήματα πελατών.

## 5. Τοπική εκτέλεση

Ανοίγουμε τερματικό στον φάκελο `Distillogic/backend` και εκτελούμε:

```powershell
npm install
npm run dev
```

Μετά ανοίγουμε:

```text
http://localhost:3000
```

Δεν ανοίγουμε πλέον τα HTML με διπλό κλικ και δεν χρησιμοποιούμε έναν ξεχωριστό απλό static server, επειδή η φόρμα χρειάζεται το API του Node server.

Χρήσιμες εντολές:

```powershell
npm run check
npm test
npm start
```

- `check`: ελέγχει τη σύνταξη των backend αρχείων.
- `test`: εκτελεί τους αυτοματοποιημένους ελέγχους.
- `start`: ξεκινά τον server χωρίς αυτόματο restart.
- `dev`: ξεκινά τον server και τον επανεκκινεί όταν αλλάζει backend αρχείο.

## 6. Αρχεία και ευθύνη τους

- `src/server.js`: Ξεκινά και σταματά σωστά τον server.
- `src/app.js`: Ρυθμίζει την ασφάλεια, τα routes και τη φιλοξενία του frontend.
- `src/config.js`: Διαβάζει τις ιδιωτικές ρυθμίσεις από το `.env`.
- `src/routes/project-enquiries.js`: Ελέγχει τη φόρμα και τα uploads.
- `src/services/enquiry-destination.js`: Είναι ο σύνδεσμος προς το CRM.
- `test/project-enquiries.test.js`: Περιέχει τους αυτόματους ελέγχους.
- `.env`: Ιδιωτικές ρυθμίσεις του συγκεκριμένου server. Δεν ανεβαίνει στο GitHub.
- `.env.example`: Δημόσιο υπόδειγμα χωρίς κωδικούς.

## 7. Σύνδεση με το CRM

Η σύνδεση με το Onix έχει υλοποιηθεί μέσω του ειδικού endpoint:

```text
POST /api/v1/website-enquiries
```

Το endpoint δέχεται μόνο server-to-server αιτήματα με Bearer token. Δημιουργεί ή επαναχρησιμοποιεί την εταιρεία, καταχωρίζει νέα επικοινωνία, διατηρεί όλα τα στοιχεία του project σε δομημένη μορφή και αποθηκεύει τα συνημμένα. Τα έγγραφα μπορούν να ληφθούν μόνο από συνδεδεμένο χρήστη του CRM.

Τοπικά το Onix web χρησιμοποιεί τη θύρα `3100`, επειδή η θύρα `3000` χρησιμοποιείται από τη DISTILLOGIC. Το Onix API χρησιμοποιεί τη θύρα `4000`.

Για να γίνει η πραγματική σύνδεση χρειαζόμαστε από τον συνάδελφο που δημιούργησε το CRM:

1. Τη διεύθυνση API ή webhook.
2. Τον τρόπο authentication, π.χ. Bearer token ή API key.
3. Τα ακριβή ονόματα των πεδίων που περιμένει το CRM.
4. Τον τρόπο δημιουργίας lead/project enquiry.
5. Τον τρόπο αποστολής συνημμένων αρχείων.
6. Ένα δοκιμαστικό περιβάλλον ή test account.
7. Τεκμηρίωση των πιθανών HTTP responses και σφαλμάτων.

Όταν είναι διαθέσιμα, προσαρμόζεται μόνο το `src/services/enquiry-destination.js` και στο ιδιωτικό `.env` ορίζονται:

```text
NODE_ENV=production
ENQUIRY_DESTINATION=crm-webhook
CRM_WEBHOOK_URL=https://crm.example.com/api/project-enquiries
CRM_BEARER_TOKEN=το-ιδιωτικό-token
```

Για το τοπικό Onix η διεύθυνση είναι:

```text
CRM_WEBHOOK_URL=http://127.0.0.1:4000/api/v1/website-enquiries
```

Το πραγματικό token δεν πρέπει να σταλεί σε email χωρίς ασφάλεια, να γραφτεί σε HTML/JavaScript ή να ανέβει στο GitHub.

## 8. Χρειάζεται βάση δεδομένων;

Για τη σημερινή λειτουργία όχι απαραίτητα. Αν το CRM είναι το επίσημο σύστημα καταγραφής, ο backend μπορεί να προωθεί εκεί τα αιτήματα χωρίς δεύτερη βάση δεδομένων στη σελίδα.

Μια ξεχωριστή βάση θα χρειαστεί αν θέλουμε λογαριασμούς χρηστών, διαχειριστικό panel, κατάσταση αιτημάτων μέσα στη σελίδα, ιστορικό, retry queue ή περιεχόμενο που αλλάζει δυναμικά. Δεν πρέπει να δημιουργήσουμε δεύτερη αποθήκη προσωπικών δεδομένων χωρίς επιχειρησιακό λόγο, πολιτική διατήρησης, backups και έλεγχο πρόσβασης.

## 9. Παραγωγή και ασφάλεια

Ο production server χρειάζεται:

- Node.js 20+ ή container runtime.
- HTTPS με έγκυρο πιστοποιητικό.
- Reverse proxy, συνήθως Nginx ή το αντίστοιχο control panel.
- Process manager ώστε η εφαρμογή να επανεκκινεί μετά από crash ή reboot.
- Firewall και περιορισμένη πρόσβαση SSH.
- Μυστικά σε server environment variables, όχι μέσα στο repository.
- Monitoring και καταγραφή τεχνικών σφαλμάτων χωρίς προσωπικά δεδομένα.
- Ενημερώσεις ασφαλείας των dependencies.
- Antivirus/malware scanning πριν ενεργοποιηθούν uploads πραγματικών enterprise εγγράφων.
- Πολιτική απορρήτου, περίοδο διατήρησης δεδομένων και διαδικασία διαγραφής.
- Backup στο CRM και δοκιμασμένη διαδικασία ανάκτησης.

## 10. Τι δεν έχει ακόμη ενεργοποιηθεί

- Πραγματική αποθήκευση στο CRM.
- Email notifications.
- Malware scanning συνημμένων.
- CAPTCHA υψηλότερης προστασίας.
- Production domain, HTTPS και reverse proxy.
- Πολιτικές Privacy, Terms και Cookies πίσω από τα αντίστοιχα footer links.

Αυτά θα υλοποιηθούν αφού γνωρίζουμε το CRM API και το είδος του server στον οποίο θα γίνει η φιλοξενία.
